# Sandboxed Quickshell plugins

Status: an admitted, sandboxed Quickshell worker now renders through the Rust controller and a native Qt item. The existing shell has an explicit native activation path and a first-party graphical reviewer over the command contract. Private-display tests cover review/approval/activation/revocation, GPU effects, keyboard and wheel/touchpad input, popups, integer-scale resizing, a native-MPRIS media widget, and brokered notifications. This remains a development-only, uninstalled preview; full demo parity and desktop acceptance are unfinished. Plugins declaring sandbox execution never enter the trusted QML loader. Existing third-party plugins without that declaration remain in-process and must still be treated as trusted code.

## Size constraint

Build the smallest system that preserves real Quickshell across process isolation. Prove one complete plugin before generalizing. Keep experiments outside the repository; do not land dependency forks, a replacement renderer, a provider catalog, or an extensible policy framework to make a demonstration work. Logical responsibilities do not require separate crates or services.

## Contract

The trusted shell owns real desktop windows, placement, input focus, dismissal, and surface lifetime. Each plugin runs real Quickshell against a private display inside its own sandbox. QML, JavaScript, bundled native modules, and helper processes execute there, never inside the trusted host.

A Rust controller owns plugin identity, grants, bounded requests, worker supervision, and revocation. Qt glue only presents surfaces and forwards host-authorized input. Plugins do not receive host QObjects, the real compositor socket, ambient session D-Bus, host command execution, or general host filesystem access.

Preserve these capabilities, subject to explicit resource grants:

| Capability | Required behavior |
| --- | --- |
| Custom visuals | QML/JS, animations, transparency, accelerated effects, and native QML modules |
| Surfaces | Embedded bar widgets, panels, popups, overlays/pets, multiple surfaces, and eventually replacement bars |
| Helpers | Bundled processes inherit the plugin sandbox and are terminated with it |
| Resources | Private storage, selected files, narrowly filtered services, and separately approved network access |
| Host effects | Narrow typed operations where direct resource grants cannot safely meet the need |
| Permissions | Requests are not grants; approval is tied to an exact revision and authority set; expansion requires new approval |

Compatibility is not permission to retain ambient authority. Existing shell object injection and service imports need adapters or explicitly unsupported behavior, not insecure fallback. Host arbitrary command execution is a separate full-authority decision, not an ordinary helper permission.

## Threat model

Assume plugin code, native modules, helpers, manifests, and protocol messages are malicious. Protect host files and services, other plugins, permission records, shell availability, and input outside the plugin's assigned region. Authenticate identity from the controller-created connection, not a plugin-supplied identifier. Bound messages, surfaces, buffer dimensions, rates, memory, and processes before accepting untrusted workloads.

The kernel, graphics driver, installed runtime, compositor libraries, controller, and presentation bridge remain trusted. A granted GPU render node exposes driver attack surface; it is not equivalent to CPU-only isolation. Transparent pixels are not automatically click-through, and alpha must not substitute for an explicit input region. Worker crashes, malformed input, and teardown must not take down the shell.

Prefer existing isolation and lifecycle mechanisms: Bubblewrap, systemd resource limits, filtered D-Bus connections, and portals where applicable. Do not create another implementation of mechanisms they already provide. Fail closed when required isolation cannot be established.

## Staged implementation

Product priority: adversarial testing is deferred at the user's request while the permission, enable/disable, and runtime-management surfaces are built. Before release, return to malformed Wayland clients, oversized requests/buffers, request floods, controller crash/hang containment, and isolation between simultaneously running plugins, then run disposable-VM acceptance. The exploratory raw-client fixture was removed rather than counted as coverage: its object-ID/binding handshake was not validated, so its apparent disconnections did not establish the intended containment results. Existing focused lifecycle and boundary tests remain, but they do not satisfy this broader release gate.

1. Prove private surface hosting with real Quickshell: animation, keyboard input, popup repositioning, transparency/input regions, accelerated effects, resize/scale, focus, worker death, and measured overhead. Compare Qt hosting with Smithay before selecting the smallest maintainable implementation.
2. Establish the minimal Rust controller and Qt bridge. Add connection-bound identity, versioned bounded IPC, disconnect behavior, and surface cleanup. These are logical boundaries, not a commitment to three crates.
3. Complete per-plugin filesystem/process isolation, private writable storage, resource limits, helper cleanup, and native-module packaging. Validate using hostile fixtures.
4. Add only the first grants: private storage, a selected read-only directory, one filtered service connection, and one brokered operation. Specify crash-safe publication and recovery before selecting persistence; atomic single-writer JSON is a candidate, not a settled design.
5. Test revocation during activity and persistence failures. Close admission first, invalidate stale requests and replies, withdraw surfaces, and terminate the worker tree when a directly granted resource must be removed. Revocation cannot undo completed writes or erase data already read.
6. Port representative plugins, starting with an animated widget/keyboard panel and a helper, then an overlay/pet, service/network integration, and a replacement bar. Expand APIs only in response to demonstrated need.
7. Harden an opt-in preview: protocol fuzzing, persistence fault injection, resource exhaustion, and graphical acceptance tests in a disposable environment. Verify scaling, multiple monitors, suspend/resume, and recovery before enabling it.

Do not build the permission framework before the surface-hosting exit gate passes.

## Feasibility findings

Temporary tests on Quickshell 0.3.1, Qt 6.11.2, Mesa 26.2.1, and Intel Arc B390 established the following. These are self-authored happy-path fixtures, not a security assessment or a compatibility guarantee.

| Test | Observation |
| --- | --- |
| Qt host, software buffers | Real `PanelWindow` and `FloatingWindow` rendered; synthetic private-display input reached QML text and click handlers |
| Qt host, accelerated buffers | Rendered on the GPU only after temporarily adding the missing compositor DMABUF integration and device feedback; no patched dependencies were installed |
| Qt host, popup | The installed XDG shell v1 support triggered Quickshell's hide/reopen reposition fallback and the popup immediately closed |
| Qt host, shutdown | Initial client-buffer teardown crashed; explicitly disconnecting private clients before host shutdown avoided the crash in subsequent short tests |
| Smithay 0.7, headless | Unpatched Smithay accepted real Quickshell GPU buffers; the captured frame showed the panel, animated widget with shadow, edited text, and open popup |
| Smithay popup/input | Private synthetic pointer/keyboard events reached QML; popup reposition was acknowledged and the popup remained present at capture |
| Helper | A worker-spawned helper ran inside Bubblewrap and confirmed the real home directory and session-bus path were absent |
| Qt GPU bridge | A small native Qt item imported two Rust-composited DMABUFs through EGL and Qt's public texture interface, without CPU pixel transport; rendering and input passed with Qt's threaded render loop |
| Input regions | The bridge received the worker's input region; a click in a subtracted region reached a host-owned item underneath, not the worker's click handler |
| High DPI and resizing | At integer scale 2, rendering remained correct, the worker window accepted a change from 480×280 to 620×300, and input remained correctly mapped after resizing the host item |
| Native module | A bundled native QML module loaded inside the sandbox after using a relative library RUNPATH; it confirmed the host home and session-bus paths were absent |
| Host dismissal and teardown | A host click dismissed the private popup and withdrew keyboard focus; producer exit removed the Qt scene-graph content, verified in a captured frame |

Smithay resolves the two protocol gaps encountered in the Qt experiment and now has a working headless Qt embedding proof. The two-buffer prototype uses conservative GPU waits and a frame acknowledgement: the currently displayed buffer remains unchanged while the next buffer is rendered. Readback is used only for test capture, not presentation. Its hardcoded geometry, synchronous test transport, fatal error handling, and incomplete surface policy must not be promoted into the trusted shell.

A short, sequential 800×480 comparison measured median frame intervals of 16.66 ms for both the direct fixture and the bridge. The p95 interval was 16.88 ms direct and 17.40 ms through the bridge. The direct Qt fixture used 113,568 KiB proportional memory; the bridge's Qt host, worker, and inner Rust compositor together used approximately 209,839 KiB, about 94 MiB more. These are single-run, debug-build fixture measurements, not a production benchmark, input-latency measurement, or full GPU-memory accounting.

Real desktop focus/click-through, fractional scaling, multiple monitors, dynamic output changes, complete popup grabs, sustained resource behavior, and adversarial crash containment remain unverified. The headless evidence is sufficient to begin the minimal runtime implementation, not to enable it for user plugins or claim the shipping validation gate has passed.

## Worker restriction implementation

### Revision and publication rules

Approval names a content-addressed snapshot, not the live checkout. Snapshotting copies bounded regular files/directories without following links, preserves executable intent, excludes Git administrative data, and hashes the copied bytes and relative paths. The initial limits are 64 MiB, 4,096 entries, and 16 directory levels. Symlinks, hardlinked files, and special files are rejected; bundles must currently contain their actual helper/native-module files. The requested authority comes from that copied manifest. Source updates cannot silently replace an approved revision; modified snapshots fail verification.

Grant publication uses one controller-owned JSON record per plugin, a stable writer lock, and a durable pending marker. Write and synchronize the pending marker before replacing a record; synchronize the new record and parent directory before removing and synchronizing away the marker. Readers reject pending, malformed, missing, or mismatched state. Explicit recovery disables authority instead of completing a pending approval. Marker removal is the visibility commit point: an interrupted operation after that point may have committed exactly the approved record even if its caller received no acknowledgement; before it, admission remains closed. Tests inject errors and abrupt process exits at seven publication checkpoints.

Revocation closes admission before stopping the recorded service and verifies descendant exit before reporting success. A replacement service identity is recorded before launch, and the previous service is stopped before publishing the replacement. The controller rechecks its actual service identity, epoch, revision, and approval before admission; it subsequently checks authority during its event loop. The persisted unit identity permits cleanup after the launching shell disappears. Tests cover stale epochs, rejected same-user impostors, active-controller revocation, interrupted publication during operation, malformed state, writer contention, and explicit recovery. The presentation and notification integration tests below additionally cover surface withdrawal and in-flight helper cleanup.

The preview manifest adds `sandbox: { version: 1, requests: { ... } }` alongside the existing plugin metadata. Omitting `sandbox.entryPoint` selects the shared worker loader for the original manifest's `entryPoints`; an explicit `entryPoint: "worker.qml"` retains the custom worker path. Requests and grants are separate; every authority defaults to denied. Grant records describe named read-only directory slots, optional network access, one exact MPRIS service, notifications, and private storage. Directory/network/media/notification resource bindings are connected to the worker launcher; storage still fails startup rather than being silently ignored. The private-storage API versus persistent-filesystem choice remains unresolved.

The shared runtime supports one `bar-widget` and optional `service`/`overlay`, requiring exact, unique kind/entry-point matches at review. CMake stages one host-owned `worker.qml`, unchanged `qs.Ui`/`qs.Commons`, and `PluginShellApi` under `lib/plugin-runtime/shell`. The controller opens the runtime beside its own executable and mounts the pinned directory read-only at `/runtime`; only the worker receives `OMARCHY_PATH=/runtime`. It does not mount the host repository, configuration or service tree. These host-versioned libraries execute inside the existing sandbox, not in the desktop shell, and do not replace the exact-revision approval of plugin bytes. Runtime directory replacement cannot redirect the opened mount; pathname sockets inside it remain denied by Landlock. Missing runtime files and QML load failures do not fall back to the trusted loader.

This loader retains own-service and own-overlay instances and supplies local lifecycle/bar facades without a host command executor or settings writer. Its initial single-screen bar placement follows the manifest's default section, not the real host bar slots; settings/theme synchronization, tooltip forwarding, cross-panel handoffs and service-only readiness remain gaps. A CMake-staged private-display test loads plugin-only entry files, including a filename containing space and `#`, and verifies scoped service lookup, two panel open/Escape-close cycles with retained service state, click-through and revocation. A separate original-GitHub experiment now passes search/typing/two-Escape behavior against this packaged runtime with only the sandbox manifest addition and no vendored host modules. Captures were visually inspected; this remains no-authority UI evidence, not authenticated or real-desktop parity.

### Implemented boundary primitives

`native/plugin-host` is one Rust crate. Its worker bootstrap applies Landlock and a seccomp filter after Bubblewrap establishes isolation, before untrusted code executes. It is not a complete plugin controller by itself.

Read-only bind mounts do not make Unix sockets read-only: connecting to a socket beneath a directory grant could otherwise confer extra host authority. The initial runtime therefore requires Landlock ABI 9 and explicitly permits private controller sockets. Host directory descriptors are rejected as IPC grants. Separately, the launcher-created private tmpfs directories permit local sockets so helpers can communicate with each other; symlinking from those directories to an ungranted host socket remains denied. Abstract Unix connections and signals are scoped; namespace creation and selected dangerous kernel interfaces are denied, while ordinary threads, processes, and helper execution remain available. Failure to install any required restriction is fatal to worker startup; there is no weaker fallback.

Unit tests check the filter's architecture, syscall, namespace, and socket-family decisions. Fresh-process kernel tests verify allowed/denied sockets, rejection of a directory as IPC authority, ordinary thread creation, and helper inheritance. The actual Rust restriction module was also linked into the temporary headless Quickshell test: GPU rendering, native modules, helpers, high-DPI rendering, resized input, and host-owned dismissal continued to work. Kernel-dependent tests explicitly report a skip after verifying fail-closed behavior on unsupported systems.

The trusted per-plugin controller runs in a generated transient user service with memory, swap, process, file-descriptor, and CPU ceilings. Both launcher and controller verify kernel cgroup settings; the controller checks before starting untrusted code. A watchdog is refreshed from the healthy controller event loop, not an independent thread. Stop/revocation checks kernel cgroup population rather than trusting a successful manager reply. Kernel tests verify explicit stop, controller crash, controller hang, process exhaustion, memory exhaustion, and host-channel EOF, including descendant cleanup. The tests do not establish GPU-memory ceilings.

The private host/controller channel uses non-blocking sequenced Unix records, capped at 4,096 bytes and four descriptors, with bounded kernel send queues and no internal unbounded queue. Descriptor transfers are close-on-exec and rejected/truncated records close their received descriptors. Admission checks the peer's UID, kernel-provided socket pidfd, and membership in the specific launched service. Versioned control records have a bounded dispatch/rate budget and a three-second host lease. The real controller executable passes stop, disconnect, silent-host, replay, malformed-record, and unexpected-message tests. This is not the worker's Wayland endpoint or an arbitrary host-command RPC.

The initial Bubblewrap profile strictly separates namespaces, clears the environment, mounts descriptor-pinned bundle/bootstrap/private-socket inodes, drops capabilities, and closes inherited descriptors before applying worker restrictions. Named directory grants appear read-only under `/grants/<slot>` and retain the selected directory's device/inode identity. Network access remains isolated unless explicitly granted; that grant includes the host network namespace, including loopback, plus resolver and certificate configuration. Tests use only a temporary loopback listener, not external services. Graphics workers receive only the selected render node and its device-specific sysfs subtree, not a modesetting node or all host devices. Persistent storage still needs an agreed contract and integration.

Supervised worker tests verify read-only files, pathname replacement resistance, absent host paths/environment, denied and granted network access, denied namespace creation, socket confinement, private helper IPC, inherited-descriptor cleanup, and temporary-space exhaustion. Selecting a host directory does not authorize its sockets, even through a symlink from private writable space.

### Selected media service

An approved media grant launches `xdg-dbus-proxy` inside the same resource-limited controller service. The worker receives only its descriptor-pinned filtered socket at `/run/plugin/media`; the real session-bus socket remains absent and inaccessible, including through a read-only directory grant. The proxy is constructed from the admitted grant, not from worker-supplied rules, and the launcher rejects a prepared proxy whose selected name does not match that grant. Missing proxy support, readiness failure, or proxy exit fails closed. The controller waits at most one second for proxy readiness before starting plugin code.

Rules expose one exact `org.mpris.MediaPlayer2.*` name chosen by the approver, without a wildcard grant. Calls are restricted to `/org/mpris/MediaPlayer2`: property `Get`/`GetAll`, introspection, and `Play`, `Pause`, `PlayPause`, `Stop`, `Next`, `Previous`, `Seek`, and `SetPosition`. Property-change and seek signals are admitted from that endpoint. `OpenUri`, application quit/raise, property writes, name ownership, monitoring, other interfaces/methods, and other object paths are not granted. Property reads apply to properties on that selected object; the proxy does not inspect the requested interface argument inside `Get`/`GetAll`. Volume, rate, shuffle, and loop-state setters are therefore currently unsupported even when a player advertises them.

This is a filtered D-Bus connection, not an exact-name packet router or a rate-limited method broker. Upstream filtering associates rules with unique owners and may retain them after a well-known name is released. Explicit revocation kills the entire proxy/worker service and closes established connections; replacing a selected owner is not itself a permission-revocation operation. These semantics, and the trusted selected application's behavior, are part of the resource contract. [Upstream proxy policy](https://github.com/flatpak/xdg-dbus-proxy/blob/main/xdg-dbus-proxy.xml)

Tests create a private bus with no activation directories and two fake players; no active media application is contacted. The sandboxed worker can read properties and control the selected player, but cannot call forbidden methods, access an unrelated alias or player, bypass rules through unique names, own a service name, monitor the bus, or connect to the real test bus through a directory grant/symlink. Proxy shutdown closes an already-connected socket. An admitted real-Quickshell test now copies the existing `shell/plugins/services/media/BarWidget.qml` byte-for-byte, alongside its model and visual controls, into the approved test bundle. It verifies the selected player's metadata, animated label pixels, playback toggle, middle-click next, wheel previous/next, album art, all three popup controls, host dismissal, tooltip reopening/closing, and session termination after durable revocation. The unrelated fake player survives.

The port's adapter is worker-local QML backed by `Quickshell.Services.Mpris`, not the real shell's service object. The approved service set contains exactly one player, so no additional source is made visible or selectable. Test packaging retains the real color/style calculations but removes host theme watchers and compositor probes; it uses data-only defaults and replaces `HyprlandFocusGrab` with private-popup dismissal from the host. The original widget, buttons, borders, and label animation remain unchanged. This proves a selected-player port, not ambient compatibility with the complete media service: PipeWire arbitration, shell-wide OSD and configuration, multiple-player selection, and automatic access to host album-art paths are not granted. The album art in this test is a bundled asset; external artwork still needs an explicit applicable file/network grant. Packaging is a test fixture, not a public plugin SDK or installer.

Frame review caught two adapter errors that state-only checks missed: subpixel tooltip sizing could elide the final word, and an opacity-based `visible` binding could briefly reopen a popup after private `popup_done`. The adapter now rounds intrinsic text width upward including border insets, withdraws hover help immediately on popup takeover, and guards host-dismissed popups until the next explicit open. Tests wait for untruncated tooltip text and actual rendered pixels, require transparency after dismissal, and reject a media popup reappearing while tooltip interaction continues. The final captured frame sequence was inspected for these transitions as well as label motion and popup layout.

### Text-only notification broker

An approved notification grant adds one descriptor-pinned private socket at `/run/plugin/notify`. Quickshell can invoke `Process { command: ["/bootstrap", "--notify", title, body] }`; the helper inherits the worker's restrictions and connects only to that fixed endpoint. It does not expose an arbitrary method, executable, desktop action, replacement identifier, image, application identity, or bus connection. Requests are versioned, descriptor-free JSON records with exactly `version`, `title`, and `body`. Titles are limited to 160 UTF-8 bytes and bodies to 2,048 bytes; control characters and bidirectional override/isolation marks are rejected, except body newlines.

The Rust controller authenticates each peer's UID, socket pidfd and membership in its own service, then checks the current recorded unit, epoch and notification grant under the publication lock before starting delivery and before acknowledging completion. Identity is derived from that record. Delivery invokes the fixed `$OMARCHY_PATH/bin/omarchy-notification-send` helper with low urgency, a five-second expiry, a plugin-labelled title/application name, and escaped body markup. Both text positionals carry trusted prefixes because the existing helper recognizes option flags in those positions. No worker text is interpreted as shell code or a notification option.

The broker accepts at most 32 connections per second, authenticates at most four per dispatch, retains at most four waiting clients for one second, and permits one in-flight delivery with no effect queue. A two-token per-controller budget replenishes one token every 30 seconds. The delivery helper runs under a one-second process-group timeout in the same bounded service; the event loop polls completion without waiting synchronously. Requests receive `delivered`, `invalid`, `busy`, `rate_limited`, or `failed`; the worker helper waits at most three seconds. An explicit host relaunch starts a new budget; there is no automatic worker restart policy.

Revocation closes new admission, kills in-flight helper descendants with the whole service, and prevents a stale success acknowledgement. It cannot undo a notification already accepted by the desktop service; sent notifications are not withdrawn, and delivery has no transactional cancellation or exactly-once guarantee. `delivered` means the existing helper returned success, not proof that a user saw the notification.

Tests use a private recorder, never the active notification service. They verify denied grants, rejected same-user outsiders, malformed/identity-bearing/descriptor-bearing requests, option and body-markup isolation, busy/rate/timeout behavior, and revocation during delivery. A parser test runs the real Omarchy notification helper against a recorder-only `busctl` stub and checks every typed argument, including absent actions and image hints. A separate admitted real-Quickshell test completes two native `Process` requests through the restricted helper.

### Integrated presentation

The optional `graphics` feature runs an unmodified Smithay private compositor in the admitted, resource-limited controller. It starts real Quickshell only after the host configures a viewport. The initial compositor accepts toplevels, layer surfaces, and popups, with limits on clients, surfaces, input rectangles, and buffer dimensions. Native modules can be bundled under `native/` in the approved snapshot. GPU rendering, native-module imports, and helper execution do not grant access to the real compositor or session bus.

Inside the assigned canvas, layer surfaces stack as background, bottom, ordinary windows, top, and overlay; later surfaces within a layer appear above earlier ones. Committed layer changes affect rendering and hit testing together. Anchored margins inset stretched dimensions, explicit sizes between opposite anchors remain centered, and arithmetic bounds extreme margins and sizes to the private viewport policy. Popups stay directly above their own parent tree, below higher layers. Their positions use committed XDG geometry and explicit window-geometry offsets; bounded positioners use Smithay's flip/slide/resize constraints against the assigned canvas. A positioner that requests no adjustment can remain clipped outside it.

These are private composition rules, not permission to choose a real desktop layer or reserve screen space. Plugin exclusive zones do not reserve space on either the real desktop or the private canvas. The trusted shell must explicitly choose any actual edge, overlay, replacement-bar placement, and reserved area. Keyboard-none layer clicks preserve existing private keyboard focus; other layer policies can receive focus only after host-authorized input, never by demanding an exclusive desktop grab. Complete popup-grab semantics and implicit client-decoration geometry remain unfinished.

A separate real-Quickshell fixture deliberately creates an animated masked overlay before its inset bar and creates the background last. It checks stacking independent of creation order, moving the overlay to the bottom layer, matching click targeting, text focus retained across a keyboard-none click, input-mask holes, a fully visible edge popup, acknowledged reposition to the opposite edge, input at the committed new position, and host dismissal. Its captured frame sequence was inspected for animation, bar insets, intentional layer overlap, popup text fitting at both edges, and final withdrawal. This is a private overlay/bar composition proof, not an installed replacement bar or live-desktop acceptance test.

Two controller-owned, linear ARGB buffers carry completed output to Qt. Untrusted worker buffers and fences are not forwarded to the host. Versioned presentation records validate dimensions, stride, format, descriptor counts, mask bounds, generation, serial, and buffer ownership. The producer never writes the displayed slot, and cannot advance until the host acknowledges the next frame. Its GPU wait occurs in the supervised controller; Qt inserts a completion fence and polls it with zero timeout, then acknowledges through Rust. A stuck controller stops refreshing its watchdog. This does not protect against a kernel/driver failure or establish GPU-memory quotas.

The optional `qt-bridge` feature uses CXX to keep decoding, admission, launch, leases, and service cleanup in Rust. The Qt QML module exposes `PluginView` with explicit host-selected store, plugin identity, controller executable, and viewport. It cannot approve revisions or broaden grants. Startup and cleanup run on a background thread, with 64 input commands and eight presentation updates of queue capacity; overload, malformed records, EOF, or lease expiry terminate that session. Dropping the host item does not synchronously wait for the service manager. An error clears its input mask and scene-graph content without terminating the host.

Input masks compose each mapped surface's independent input region, including subsurfaces, clipped to its own view and the assigned viewport. The item takes keyboard focus only after a host pointer press. Keys, including Escape press and release, go to the focused worker control so its existing clear-search, menu and panel-close behavior can run. Focus loss and explicit host dismissal separately clear private keyboard focus, cancel pressed input/grabs, and dismiss popups. The shell still must provide outside-click, workspace, monitor-change, and owner-switch policy when integrating the item. Fractional scaling, multiple outputs, complete popup grabs, and scene-graph/context-loss stress testing remain unfinished. The viewport is one resizable canvas with integer scale, not a finished multi-surface desktop placement API.

After host pointer activation, the private compositor honors the topmost mapped top/overlay layer's exclusive keyboard request. This lets the original KeyboardPanel acquire focus when opened from a keyboard-disabled bar icon, then retain it when its brief exclusive prime becomes on-demand. Unmapping or switching to keyboard-none removes that focus. Host dismissal and resizing disarm automatic private focus until another host pointer press; an exclusive layer left running cannot rearm it. The private `focus` test covers the prime, actual key delivery, persistent exclusive mode, dismissal, reactivation, keyboard-none and unmapping, including continued client frames and rejected keys during the unfocused intervals. This is private-display behavior, not proof of real-desktop focus or complete popup grabs.

Scrolling uses its own 28-byte control record with no descriptors: bounded position, horizontal/vertical deltas, and an exact wheel/finger/end source. Rust validates both encoding and decoding, rejects unknown sources, invalid zero/end combinations, and magnitudes outside ±4096, then re-hit-tests within the current viewport without acquiring keyboard focus. Wheel deltas preserve partial detents through Wayland `axis_value120`; finger deltas are logical pixels and end records stop both axes. The Qt item respects its input mask and resize pause, maps pixel deltas into the private canvas, and preserves the already-applied natural-scroll direction. The Qt integration test verifies horizontal/vertical wheel input, a half-detent, finger pixels, and gesture completion after moving and scaling the item. [Qt wheel-event semantics](https://doc.qt.io/qt-6/qwheelevent.html)

Quickshell's standard output is redirected into the controller's existing bounded worker-error pipe, so configuration failures are diagnosable without adding an unbounded log queue or a worker-selected host log destination.

The host explicitly calls `PluginView.configure(logicalWidth, logicalHeight, scale)` to change that canvas without restarting the worker or changing its approval. Changing the Qt item's own rectangle alone still scales its existing canvas. The Rust session retains one in-flight resize and coalesces later requests to the latest requested geometry. Each accepted configuration announces its logical viewport and strictly increasing generation before describing two new output buffers; unsolicited generations, geometry mismatches, mixed-generation buffers/masks, and stale acknowledgements fail closed. A new generation cannot overtake an unacknowledged old frame, and a subsequent resize waits for the first new frame to be presented. A coalesced request that returns to the current dimensions still receives a fresh generation, so input cannot remain paused waiting for a nonexistent acknowledgement.

Qt keeps its old image while replacement buffers arrive, then replaces the imported scene-graph node on the first new frame. It exposes `resizing` and suppresses private input until a newer generation matching the requested geometry has actually completed presentation. Resizing cancels private keyboard/button state and popups; later interaction must reacquire focus. The private output updates its mode and integer scale, reconfigures anchored layer surfaces, and explicitly sends per-surface preferred buffer scales through Smithay's compositor-v6 support, including newly created or subsequently committed surfaces. Output-scale announcements alone did not correctly update all worker buffers in the tested Qt configuration; the real scale-transition test exposed and verified this requirement. Old modes are removed from the controller's own mode list to keep that state bounded. [Smithay output API](https://docs.rs/smithay/0.7.0/smithay/output/struct.Output.html)

The Qt integration test hosts its trusted Quickshell window on a second private display. Pointer focus, subsequent typing, and popup clicks traverse Qt and the admitted controller into the sandboxed worker. It moves/shrinks the host item, resizes the private viewport from 800×480 at scale 1 to 640×400 at scale 2, and checks an edge click and further typing against the new coordinate mapping. A second burst returns to the same dimensions and must restore input. GPU readback checks the worker's retained text, responsive panel, popup dismissal, and interaction indicators; after durable revocation it checks that plugin pixels disappear while host-owned animation remains. Before/after captures and a short test-frame sequence were visually inspected. These tests never inject input into the active desktop. They are not substitutes for the disposable-VM graphical acceptance gate.

### Development verification

The first product commands reuse `omarchy plugin add` / `install` for ingress. `omarchy plugin review <id> [--json]` finds the installed checkout through the existing catalog, publishes an immutable snapshot without executing it, and returns the revision and requested resources. `omarchy plugin approve <id> --revision <sha256>` passes explicit selections to the Rust store; neither the shell nor a future GUI writes grant records. Read-only folders, one exact media service, network, and text notifications are opt-in flags. Confirmation requires a terminal unless `--yes` is explicit. Approval is separate from activation. `omarchy plugin enable <id>` now calls the existing shell IPC, creates a trusted native surface, and waits for an actual mapped worker frame to finish presentation. The existing `disable` command routes declared sandbox plugins to durable revocation, independently of shell availability.

The hidden `omarchy-plugin-runtime` helper exchanges bounded JSON with the native `--manage` mode and reports structured failures. Its default payload path is `$OMARCHY_PATH/lib/omarchy-plugin-host`; no payload is installed by these changes. Set `OMARCHY_PLUGIN_HOST` to an explicitly built binary and `OMARCHY_PLUGIN_STORE` to a private development store when exercising the preview. The ordinary registry never returns an in-process QML URL for a manifest declaring `sandbox`, including when native support is unavailable. Existing trusted plugins without that declaration retain their current behavior.

`omarchy plugin list` now distinguishes approval from live activation; a stored unit identity is not treated as proof of a running session. Sandbox installation, update, and removal do not require a running shell. Update leaves the approved snapshot and grants unchanged and requests re-review; an update that removes the sandbox declaration is refused. Removal revokes before deleting the checkout and preserves snapshots. Disable is idempotent for a never-approved plugin. The sandbox declaration is tracked independently of its value so a malformed declaration cannot fall through to the legacy command path.

`OMARCHY_TEST_PLUGIN_HOST=/absolute/path/to/omarchy-plugin-host bash test/shell.d/plugin-review-test.sh` tests the real add/review/approve/list/update/disable/remove commands with a disposable local Git repository and a stubbed shell endpoint. It verifies that review grants nothing, only selected access is approved, an actual Git update yields a new digest without replacing old approval, reapproval does not implicitly retain old grants, and disable/removal close admission even without the shell. `OMARCHY_TEST_HEADLESS=1 bash test/shell.d/plugin-registry-contract-test.sh` runs the actual registry in offscreen Quickshell with a private runtime directory, without connecting to the live desktop. These are normal product-flow checks; the broader adversarial program remains deferred.
